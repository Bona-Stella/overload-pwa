# Overload UI v0.9 — 백엔드 연동 설계

기준일 2026-11-07 · T02-B 문서 개정. 이 문서는 PWA 작업에서 확인한 서버 계약과 후속 연동 요구사항을 구분한다. 화면·조작은 [UI 결정 로그 v0.9](../product/Overload_UI_Decision_Log_v0.9.md)의 최신 10.14절, 디로딩 도메인은 [v1.7](../product/Overload_Deloading_Design_Specification_v1.7.md), 일반 통계는 [통계 v1.4](../../../overload-server/docs/product/Overload_Statistics_and_Tracking_Design_Specification_v1.4.md)을 따른다. 실제 PWA의 색상·시각적 위계는 [Visual Theme Spec](../product/Overload_UI_Visual_Theme_Spec_v0.9.md)을 따르며 HTML은 무채색 UX 자료다. 현재 API의 요청·응답은 각 서버 계약 문서가 기준이며 시각 표현의 변경으로 계약을 바꾸지 않는다.

## 확인한 계약과 적용 범위

| 영역 | 기존 구조 그대로 사용 가능 | 수정 또는 추가 검토 |
|---|---|---|
| 루틴·주간 일정 | `RoutineController`와 `WeeklyScheduleController`의 `/api/v1/routines`, `/api/v1/weekly-schedule` 및 일정 이력. 오늘 카드와 일반 일정은 저장된 루틴 순서 및 현재 적용 일정으로 표시 가능. | 디로딩 임시 일정과 원본 참조의 저장·버전 경계, 일반/임시 쓰기 허용 조건이 필요하다. 일반 일정 이력을 임시 일정으로 덮어쓰지 않는다. |
| 세션·기록 | `WorkoutSessionController`의 START, ACTIVE/상세/종료 목록, snapshot, FINISH, takeover, 종료 후 정정·논리 삭제·선택 복구·평가·변경 이력. `InitialPlan`과 `AppliedPlan`, 완료 세트 장비·부하 방식, 유산소 실제값을 제공한다. | START부터 디로딩 기간·임시 루틴과의 소속을 권위 있게 결정하고 읽기 및 쓰기에 적용한다. 운동 진행 중 변경·정정·복구에서 해당 소속과 최초 문맥을 보존한다. |
| 볼륨·카탈로그 | V17 표준 운동 ID와 장비 원본, V18 `joint_type` 및 PRIMARY/SECONDARY 링크, V21 유산소 실제 측정과 V22 `bodyweightLoad`. 기존 세션 상세의 실제 수행값과 계획으로 세트별·종목별 볼륨 UI를 구성할 수 있다. | 공식 볼륨과 동일한 산식으로 파생한다. 숫자 표현이나 계산 위치는 구현 검증에서 정하며, 별도 저장 볼륨 컬럼을 전제로 삼지 않는다. 6종 대표 아이콘 매핑과 운영 카탈로그 분류를 확인한다. |
| 통계·성장 | `StatisticsController`의 `/api/v1/statistics/overview`와 `/api/v1/statistics/growth/exercises` 및 배치별 조회. 전체·종목·대분류·세부 근육과 역할별 집계, 기간별 실제 수행 및 계획 근거, 승인 사건을 재사용한다. | 그래프 필터에 대응하는 날짜별 종목·근육 집계 및 제조사별 참고 통계는 현재 응답의 제공 범위를 넘는다. 추가 조회 또는 응답 확장을 검토한다. 디로딩 연결 뒤 전체 실적 집계와 해당 기간만 조회하는 화면을 구분하고, 일반 계획 달성·유효 주수 및 승인 경로에는 일반 실적만 적용한다. |
| 설정 | `GET/PATCH /api/v1/workout-settings`로 고정된 세 휴식 시간(초)을 읽고 한 번에 변경할 수 있다. 로그인 세션과 CSRF 계약을 유지한다. | 디로딩 분석 설정 저장과 추천 누적·시작 자격 조회가 필요하다. 분석 설정의 수명 주기는 휴식 시간과 다르며 기존 휴식 API 확장 여부는 미정이다. |

현행 계약은 [루틴](../../../overload-server/docs/api/routine-management.md), [주간 일정](../../../overload-server/docs/api/weekly-schedule.md), [운동 세션](../../../overload-server/docs/api/workout-sessions.md), [카탈로그](../../../overload-server/docs/api/standard-exercise-catalog.md), [통계](../../../overload-server/docs/api/statistics.md), [성장](../../../overload-server/docs/api/approved-weight-growth.md), [휴식](../../../overload-server/docs/api/workout-online-write.md)에 있다. 현재 루틴 태그(V23)와 일정 즉시 적용·일별 판정(V24/G2~G3) 계약도 확인했다. 루틴 목록·공통 폼·일정 편집은 실제 클라이언트에 연결되며 T02-B 최종 실기기 승인은 별도다. 사용자용 일정 변경 이력 UI는 없지만 서버 이력 API는 유지한다. 디로딩 API·기간/임시 루틴 모델과 혼재 데이터 검증은 구현 예정이다. V18~V22의 개인 DB 적용, 운영 카탈로그 분류 품질, 실기기 동작은 별도로 검증한다.

## T02-B 현재 API 소비

`RoutineForm`은 루틴 CRUD와 nullable 태그를 저장한 뒤 `saveSchedule`로 별도 일정 PUT을 처리한다. `WeeklyScheduleApi.save`는 immediate-v1, expectedVersion, dataGeneration, timeZone, assignments만 제출하고 응답과 최신 GET의 version/assignments/appliedAt을 확인한다. ACTIVE와 버전/계정 경계 실패 시 입력 및 부분 성공을 유지한다. `HomePanel`의 overview 판정은 미판정 요일/완전✓/부분·MISSED X/REST -로 표시하며 04시 서버 작업을 클라이언트에서 실행하지 않는다. Backend 변경이나 실제 DB 적용 여부는 이 문서 개정만으로 확정하지 않는다.

## 디로딩 구현 요구사항

2026-11-07 정책 통합: [v1.7](../product/Overload_Deloading_Design_Specification_v1.7.md)과 [실제 Backend 현황 분석](../tasks/deload-v17-backend-readiness-analysis.md)을 따른다. G0~G3의 기반과 G4~G5 미구현을 구분하며 이 문서 갱신은 실제 API/DB 적용이 아니다.

### 시작 자격과 누적 분석

- 시작 자격은 v1.7 DL-15/80~84의 네 조건을 사용한다. 현재 계획2일 이상 조건은 폐기했으며 서버가 인증 사용자·현재 세대, 계정 시간대 기준 오늘 제외 직전 7일의 일반 실제 수행과 이전 완료 이후 신규 수행, 오늘 실제 수행 및 활성 세션을 확인한다. 웨이트 실제 1세트나 양의 실제 유산소 활동 1건이 증거가 된다. 미리보기는 조회이며 시작 요청에서 최신 근거와 원본·일정 변경을 재검사한다. 일반 START와 디로딩 시작이 경합할 때 한쪽만 성립하도록 상태 검사·전이를 함께 보호한다.
- 서버가 보유한 최신 상태와 클라이언트에 남은 미동기화 원본의 범위가 다르다. 오늘의 미전송 수행을 배제하고 시작을 확정하거나, 최근 실제 수행을 업로드 날짜로 판단하지 않는다. 서버 ACTIVE와 접속 기기가 아는 원본을 보호하며 타 기기 미지 상태용 전역 잠금을 도입하지 않는다.
- 유효 주수는 DL-05~14를 적용한다. 현재 주간 일정의 유효 버전과 일반 세션의 `InitialPlan`, 현재 유효한 완료 세트·실제 유산소 목표 증거를 비교한다. 일반 주간 일정은 현재 immediate-v1 계약을 따른다. 디로딩 추천 누적은 G4 후속이며 구 설계의 다음 월요일 예약 문구를 현재 일정 UI/API에 적용하지 않는다. 하루 최대 1일, 주 최대 1주, 월~일 실제 일반 수행/확정MISS 날짜의 E/N, E≤1 RESET·E>1 ADD, 다음 월요일04시 이후 검사 완료 확정, OFF/재활성화, 디로딩 중 정지, 완료 후 0·무수행 취소 시 누적 보존을 적용한다. 완료 다음 날부터 일반 운동을 허용하며 해당 주 분모는 DL-13을 따른다.
- 현재 통계의 종목 완료 판정은 재사용하되 ST-17~23의 예정 루틴 후보와 G4의 예정 외·휴식일 일반 세션 후보는 분리한다. 추천 분석의 활성 기간과 초기화 이력, 디로딩 제외·재개는 별도로 적용한다. 재동기화나 기록 정정·논리 삭제·복구 후 수행일을 기준으로 재계산하며, 확인 불가한 유산소 목표나 과거 일정을 임의로 채우지 않는다.

### 기간·임시 루틴·세션 소속

- 서버가 시작일, 기간과 방식, 진행/완료/취소 및 종료 사유·날짜를 권위 있게 관리한다. 권장 7일은 안내 기준, 10일차 종료가 자동 완료 경계다. 완료 당일까지 일반 START를 막고 다음 날 복귀한다. 무수행 취소는 즉시 복귀한다. 완전 휴식 정상 완료도 기간 이력을 남긴다. 이 개념은 API enum이나 테이블명의 확정안을 뜻하지 않는다.
- 생성은 원본 계획·배치와 승인 중량(없으면 초기 중량)을 참조한다. 임시 계획은 독립적으로 보존한다. 분할·세부 PRIMARY·다관절 정렬과 상한, 웨이트 중량 85%·장비별 내림·세트 50%·반복 보정, 유산소 속도 85%·시간 50% 및 배치 예외는 v1.7 4~8절(기존 v1.6 수치 보존)의 기준을 그대로 사용한다. 미분류는 `OTHER`와 구별한다. 완료한 날짜와 수행 원본은 고정하며, 8~10일차에는 기존 미수행 임시 루틴을 이동·수정할 수 있다. 전체 임시 루틴 삭제와 기간 취소는 별개다.
- 일반 보기의 선택값은 클라이언트의 탐색 상태다. 서버는 조회 탭과 관계없이 활성 디로딩 중 원본 루틴 및 일반 기록의 변경·삭제와 일반 운동 실행을 막아야 한다. 공통 계정·휴식 설정은 기존 권한에 따른다.
- 디로딩과 일반 운동에 하나의 활성 세션 제약을 공유한다. 수행 후 정정·논리 삭제가 일어나도 디로딩 취소·방식 변경을 막는 수행 사실을 보존한다. 활성 운동은 완료·취소·방식 변경이나 기간 경계에서 임의로 종료하지 않는다. 무수행 취소 세션을 정리할 때 다른 기기와 미전송 원본을 보호한다.

### 기록·평가·동기화

- 세트의 당시 제조사·부하 방식과 최초 계획·봉인 계획을 보존한다. 실제 수행만 이력 및 근육 통계에 포함한다. 일반 기록은 전체 실적을 조회할 수 있고 디로딩 전용 조회는 해당 기간에 연결된 기록으로 제한한다. 동일 세트는 대분류 안에서 중복 집계하지 않으며 PRIMARY와 SECONDARY를 분리한다.
- 웨이트는 실제 완료 세트의 kg×반복, BODYWEIGHT는 명시적 추가 중량만 사용한다. 유산소는 실제 활동 시간과 [거리 출처](../../../overload-server/docs/api/cardio-actual-measurements.md)를 보존하고 종류별로 표시한다. [맨몸 추가 부하](../../../overload-server/docs/api/bodyweight-additional-load.md)와 같은 규칙을 상세 UI와 통계에 적용한다.
- 디로딩은 일반 증량·유지·감량 평가, 승인 요청/해결, 공식 성장 사건을 생성하지 않도록 서버에서 차단한다. 세션 시작·스냅샷·종료·종료 후 정정/복구·승인 해결 경로에서 소속을 검사한다. 일반 승인 사건의 배치와 불변 원본은 유지하고, 디로딩 실제 수행을 승인 사건이나 성장선의 점으로 사용하지 않는다. 디로딩에서만 수행한 종목을 성장 검색 후보에 노출할지는 조회 계약에서 확정한다.
- 기존 IndexedDB DB3/schema2의 고정 START/snapshot/FINISH, UUID, `writerEpoch`·revision·ACK, 종료 후 `expectedVersion`과 tombstone을 보호한다. 24시간 세션 AUTO_CLOSED와 10일차 기간 자동 완료는 별개의 전이다. 늦은 전송·takeover·자동 완료가 겹쳐도 동일 세션의 소속과 확정 기록을 바꾸지 않고 기존 정정·선택 복구 경계를 유지한다.

## 계약 변경 후보

- 읽기에는 분석 설정·추천 누적, 시작 가능 여부와 이유, 진행 기간과 임시 일정, 과거 기간 이력, 세션의 일반/디로딩 구분 및 기간 연결이 필요하다. 쓰기에는 미리보기와 시작 확정, 분석 설정, 미수행 임시 일정 변경, 완료·취소의 역할이 필요하다. 기존 리소스 확장과 신규 리소스의 분리 여부, 경로·DTO·오류 코드·DB 구조는 구현 전 검토한다.
- 영속화 후보는 사용자·세대별 기간 식별, 원본 일정 버전/임시 계획, 불변 세션 소속, 실제 수행 여부 증거, 분석 전환·초기화 기준점이다. 기간/임시 루틴과 운동 세션이 독립적으로 보존되도록 관계를 검토한다. 기존 세션 기록의 일괄 재분류나 기존 요청 원문의 재작성은 이 설계의 전제에 포함하지 않는다.

## 추가 결정과 검증

- **기준 문서의 표기 차이.** 디로딩 v1.6의 DOC-01과 11절 도입부에는 v1.5 문구가 남아 있다. 표지·10.3절·변경 이력에 따라 v1.6을 적용한다. 결정 로그의 이전 원형 게이지·전역 전환·시작 최종 확인 화면은 10.10절에서 대체됐으며 최신 세부 표현은 10.11절을 따른다. HTML의 예시 날짜, 남은 이전 화면 핸들러 및 샘플 수치로 계약을 정하지 않는다.
- **입력 경계.** v0.9의 반복 입력은 0 미만을 막도록 명시하고, 현재 UI/세션 쓰기는 새 완료에 양의 정수를 요구한다. 0회 초안 허용 여부를 확정할 때 새 완료 검증과 기존 기록 읽기를 구분한다. HTML 예시의 완료 세트 수를 계획 세트 분모로 재사용하지 않는다.
