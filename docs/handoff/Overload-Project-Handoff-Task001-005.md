## 1. 목표 및 개발 철학

**Overload**는 iPhone 사용을 우선한 다크 모드 운동 기록 앱이다. 웨이트 트레이닝의 점진적 과부하를 핵심으로 하고, Task 005부터 유산소 활동을 같은 운동 세션에서 기록한다.

- 운동 중 입력과 화면 전환 최소화, 한 손으로 조작 가능한 집중 UI.
- **실제 수행 기록**과 **현재 승인된 진행 중량**, **운동 당시 권고**, **사후 중량 승인 이벤트**를 분리.
- 결과·측정치와 사용자의 의사결정 구분: 권고는 강제하지 않고 중량을 자동 변경하지 않음.
- 기능 동작과 데이터 보존을 세밀한 UI 폴리싱보다 우선. 실제 iPhone 키보드/Safe Area 등 후속 검증은 추적하되 새 기능의 범위 확장을 억제.
- 향후 로그인, 서버 동기화, 차트, 디로딩, 특수 세트 등을 위한 확장성은 설계하되 지금 필요 없는 기능은 선구현하지 않음.

## 2. 저장소와 기술 구조

| 영역 | 현재/계획 | 비고 |
| --- | --- | --- |
| 프론트엔드 | `overload-pwa`: React 19 + TypeScript 6 + Vite 8 | 모바일 중심 UI, `npm test`, lint, `tsc -b`, build |
| 백엔드 | `overload-server`: Java 25 + Spring Boot 4.x | Health 진단 엔드포인트가 존재. 운동 도메인/API 연동은 아직 없음 |
| DB | PostgreSQL | **미연동**; Task 006에서 사용자 소유권 포함해 설계 |
| 현재 운동 데이터 저장 | 브라우저 `localStorage` 단일 키 `overload.core.v1`, schema version `1` | 오프라인-first 동기화/백업/설치형 PWA가 구축된 것은 아님 |
| 개발 도구 | Codex: 구현·테스트·보고서 / ChatGPT: 요구사항·UX·결과 검토 | 두 Git 저장소 각각 관리 |

- 로컬 저장값은 **Origin(프로토콜·호스트·포트)별로 분리**된다. PC LAN IP·포트 변경 시 iPhone Safari에서 다른 데이터처럼 보일 수 있다. Safari 사이트 데이터를 무심코 삭제하지 말 것.
- iPhone LAN HTTP에서 `crypto.randomUUID()`가 없는 경우를 처리하는 `getRandomValues` 기반 UUID 대체 경로는 Task 004에 구현되었다.
- 개발 서버 `vite.config.ts`의 `server.host: true`는 **사용자가 iPhone 접속용으로 의도적으로 설정**함. 신뢰할 수 있는 LAN에서만 사용하고 작업 중 임의 복원하지 말 것.
- 현재 로컬 저장은 계정 간 분리, 서버 백업, 여러 기기 동기화, 완전한 네트워크 단절 후 새로 실행 가능한 PWA를 뜻하지 않는다.

## 4. 확정된 웨이트 운동 UX

### 루틴 및 세션
- 루틴에는 이름, 요일(표시는 **월→일**), 정렬된 운동 종목, 본세트 수, 최소/최대 반복 횟수, 최초 중량 등이 있다.
- 홈은 그날 요일의 기본 루틴을 선택한다. `오늘만 다른 루틴` 선택은 스케줄을 바꾸지 않는다. 기본 루틴으로 다시 선택하면 라벨도 `요일 기본 루틴`으로 복귀한다. 쉬는 날은 운동 없는 상태로 취급.
- 운동 시작 즉시 전체 운동 경과시간을 측정하되, 먼저 **별도 워밍업 화면**을 표시한다. 워밍업 세트 수/횟수는 기록하지 않는다.
- 본운동은 **한 번에 한 종목만 집중 표시**; 세트별 기록 확인, 이전/다음 탐색 및 그날 세션 한정 조정 가능.
- 중간 본세트 완료 → 설정한 휴식 카운트다운 시작, `휴식 종료`, `+30초` 지원.
- **해당 종목의 마지막 본세트 완료 → 일반 휴식 생략**, 그 종목 화면에 즉시 `다음 종목으로` 버튼 표시. 자동 이동하지 않음. 완료시각 기준 종목 간 **경과시간 카운트업**이 표시되며, 다음 종목 첫 세트 완료 시 그 종목의 휴식 카운트다운으로 전환.
- 마지막 종목까지 모두 마쳐도 **자동 종료하지 않는다**. `운동 종료 및 요약`을 사용자가 명시적으로 눌러야 이력 확정.
- 부분 완료/조기 종료도 실제 완료한 세트만 이력에 남김. 전체 완료와 `운동 기록 저장 완료`를 혼동하지 않음. 미완료 계획 수 정보가 불명확하면 추정하지 않음.
- 전체 운동 시간과 맥락별 휴식·전환 경과시간은 상단 고정. 하단 주요 CTA 고정. 4탭: **홈 / 루틴 / 기록 / 설정**, 전역 브랜드 헤더 제거. 설정은 휴식시간·로컬저장 안내·진단 등 실제 구현된 항목 중심.
- 홈 `이어하기` 카드는 워밍업/운동 중/휴식 중/종목 전환 중/종료 대기를 구별하고, 유효한 휴식/전환 시간 표시.

### 입력 UI 및 휴식 시각 신호
- 중량 입력: 중앙 숫자 직접 편집 + 좌우 **−2.5kg/+2.5kg**; 초기 중량·진행 중량 승인·운동 중 중량 변경에 공통 사용. 버튼 입력만으로 저장/승인하지 않음.
- 세트 반복 횟수: 중앙 숫자 직접 편집 + **−1/+1**. 초안만 변경; 버튼 누름 자체로 세트 완료/휴식 시작하지 않음.
- 신규 본세트 완료는 **1 이상 정수** 필요(목표 상한을 초과하는 횟수 가능). 기존에 저장된 0회 역사 데이터는 읽고 보존 가능.
- 남은 휴식이 10초 이하이면 **하단 고정 버튼 바로 위**에 `다음 세트 준비` 안내와 큰 초 숫자. 5~1초 부드러운 강조; 0초에 제거, `+30초` 후 10초 초과 시 숨김. 상단 시계도 강조. **자동 스크롤·전체 화면 플래시·소리·진동 없음**, reduced-motion 존중.

## 5. 점진적 과부하·이력 정책 (핵심 불변 조건)

### 기준 기록과 권고
- 기준 기록(benchmark)은 **같은 한 번의 실제 수행 결과**를 비교한다. 서로 다른 날짜에서 세트별 최고 횟수를 조합하지 않는다.
- 비교 조건은 최소한 루틴 ID + 종목 배치 ID + 종목 정의/구성 + 예정 세트 수 및 반복 범위 + **현재 승인된 중량**을 포함한다. 임시/혼합 중량, 비교 불가능한 구성 변경, 불완전한 실제 기록을 무분별하게 기준으로 삼지 않는다.
- 예: 10/9/7(기준) → 10/8/6(기준 유지) → 10/9/8(새 기준). 최고 기준과 최근의 더 약한 기록은 별개 사실이다.
- 모든 비교 가능한 예정 본세트가 목표 상한을 달성하면 `증량 가능` **권고**를 제시. 목표 하한에 미달하면 `감량 검토`를 제시할 수 있으나 강제 감량하지 않는다. 컨디션 저하만으로 감량을 단정하지 않음.
- 기준 기록이 여전히 증량 조건을 만족하고 사용자가 현재 승인 중량을 바꾸지 않았으면 다음 운동에서 **기존 승인 중량의 기준 근거**로 재안내 가능. 과거 기준과 최근 약한 수행이 함께 있을 수 있다.

### 중량의 세 층위
1. **최초 중량**: 신규 루틴 배치 설정 시 입력하는 값.
2. **승인된 진행 중량**: 다음 정상 세션의 기본값. 운동 중 명시적으로 승인하거나, 운동하지 않을 때 루틴 편집→`루틴 저장`으로 바꿀 수 있음. 루틴 관리 중 변경은 이미 시작된 세션을 소급 수정하지 않음.
3. **오늘만 중량**: 해당 세션에서만 적용; 승인 진행 중량과 원본 루틴을 변경하지 않음.

증량 권고가 떠도 자동으로 중량을 올리거나 반복 횟수를 최소치로 초기화하지 않는다. 새 승인 중량은 새 비교 기준이며 과거 기록은 유지한다. 같은 종목이라도 **루틴별 배치**가 다르면 진행 중량을 독립적으로 관리한다.

### 평가와 승인 이벤트
- 완료 세션 상세 하단: `이 운동의 중량 검토 결과` — 당시 승인 중량/계획 범위/실제 횟수로 `당시 증량 가능`·`당시 감량 검토`·`당시 유지`를 표시하거나 근거 불충분을 설명.
- 홈·기록 탭: **현재 루틴/배치/승인 중량** 기준의 `현재 중량 조정 검토`, 강한 최고 기록과 약한 최근 기록을 명확히 구분.
- 실제 승인 이벤트는 `WorkoutState.progressChanges` 선택 배열로 저장되며 다음을 포함: `id`, `occurredAt`, `routineId`, `placementId`, `routineName`, `exerciseName`, `previousApprovedWeight`, `nextApprovedWeight`, `source`(`routine_editor` / `workout`), `relatedSessionId?`.
- 오늘만 변경·취소·미저장 초안·동일 값 저장은 승인 이벤트가 아님. 승인 값 변경과 사건 기록은 현행 단일 로컬 저장 단위에서 함께 성공/실패하도록 처리. 사후에 과거 완료 기록을 덮어쓰지 않음.
- `relatedSessionId`는 변경이 일어난 문맥일 뿐 특정 운동 결과가 변경의 원인이라는 증명은 아니다.
- 향후 정책 변경에 대비한 **판정 알고리즘 버전 및 판정/근거 스냅샷**의 영속 설계는 Task 006에서 검토할 것. Task 004 시점의 역사적 사실로 재구성 가능한 부분과 재구성 불가능한 부분을 구분.

## 6. Task 005에서 확정·구현된 유산소 V1

### 진입 구조
- 웨이트/유산소가 하나의 운동 세션·이력에 포함됨. 웨이트 없는 **유산소 전용 루틴** 허용.
- 루틴에서 유산소를 미리 등록(웨이트 뒤 배치, 유산소 항목 내부 순서 편집). 당일 필요하면 **세션 한정** 유산소를 추가 가능하고 원본 루틴은 바뀌지 않음.
- **운동 화면 상단에 `+ 유산소 추가`를 상시 표시하지 않음.** 웨이트 완료 후 종료 영역에서 추가 가능하고, 중간에 미리 넣고 싶다면 세트/종목 편집 메뉴를 사용. 매번 유산소를 할지 묻는 강제 팝업 없음.
- 예정된 유산소는 웨이트 이후 차례로 진행하며, 건너뛰기 가능. 전체 루틴 완료 판정에 유산소의 미완료가 반영되지만 웨이트의 유효한 기준 기록까지 무효로 만들지는 않음.

### 계획 입력(운동 전)
- 종류: **러닝머신 / 실내 자전거 / 야외 러닝 / 계단 / 기타**.
- 목표 시간 중심; 목표 거리 선택, 속도 또는 페이스 중 **한 방식**, 기구에 해당하는 경사도나 저항 강도 등만 표시.
- 속도/페이스 또는 목표 거리로 실제 수행 거리를 **추정하여 확정 기록하지 않음**.
- 운동 완료 후 입력 최소화를 위해 계획 시 값을 받는 구조.

### 수행·완료 입력
- 전체 운동 시간과 **유산소 활동 시간**을 분리. 유산소 화면의 `시작`을 누르기 전 준비/기구 이동 시간은 유산소 수행시간에 포함하지 않음.
- `accumulatedMs` + `runSince` 기반 실제 활동시간. **일시정지/재개**, 화면 재진입·새로고침 시 복원. 목표 시간 초과해도 자동 완료하지 않음.
- 종료 시 자동으로 시간 계산. 사용자가 추가 입력하는 것은 **실제 거리**(측정되는 경우)와 **평균 BPM**(측정했다면) 정도이며 모두 조건에 따라 비워둘 수 있음. 타이머를 끄지 못하는 예외를 위한 시간 수동 정정은 허용하되 자동 측정치와 정정 여부를 구분 보존.
- 확인 전 초안, 미시작·시작 후 미완료·건너뛰기, 조기 종료를 구분. 확정 전에는 성과가 있다고 처리하지 않음.
- 웨이트와 유산소 이력은 함께 저장하지만 세트 수·볼륨(kg × 실제 횟수)·진행 중량·기준 기록 판단은 웨이트에만 적용. 유산소에 웨이트의 증량 정책을 적용하지 않음.
- 웨이트 중 휴식 10/5초 경고는 유산소 화면에 나타나지 않음.

### 보고서에 기재된 현재 모델
- 기존 웨이트 `exercises` 배열 유지, 선택적 `cardio` 배열 추가; 루틴/세션에 각각 계획 스냅샷 사용.
- 계획 배치 ID와 세션 활동 ID 구분. 새 유산소 데이터는 기존 `overload.core.v1` 버전 1 안에 선택 필드로 추가되며, 구 데이터에는 없는 값을 빈 배열처럼 해석해 **원문을 강제 재저장하지 않음**.
- 최종 Task 005 보고서: 기존 99개 + 신규 22개 = **121/121 테스트 통과**, 프론트엔드 lint/typecheck/build/diff-check 통과. 실기기 Safari·키보드·잠금/오프라인 재실행은 추가 검증 필요.

### V2/추후로 미룬 기능
- 웨어러블/Apple Health 연동, 자동 심박·칼로리 수집, GPS 경로, 세밀한 인터벌 데이터, 유산소 자체의 점진적 과부하/디로딩 권고.

## 7. 현재 데이터 신뢰성과 한계

- 저장 실패 시 진행 중 메모리 입력은 가급적 유지하고 실패를 표시하되 **페이지 재로드 후 유실될 수 있음**. 로컬 저장을 영구 백업이라고 설명하지 말 것.
- 손상 데이터·상위 미지원 버전은 원문 자동 삭제/덮어쓰기 대신 편집 차단. 저장 실패와 다중 탭 동시 편집 충돌 방어 존재(서버 동기화나 분산 동시성 보장은 아님).
- 운동 진행 시각은 timestamp 기반으로 계산. 화면을 벗어났다가 돌아오더라도 기존 완료·초안·휴식/전환·유산소 활동을 복원하는 방식.
- 실제 iPhone Safari의 가상 키보드, 노치/Safe Area, 잠금/백그라운드 제한, 다른 기기 동기화 등은 아직 미확인/미구현 범위를 명확히 구분해야 한다.

## 9. Task 005.5 설계 시 가장 먼저 합의할 문제

**확정된 사실**: 현재 사용자의 데이터는 iPhone Safari의 로컬 `overload.core.v1`에 저장되어 있고, 서버 사용자 계정과 연결되지 않았다. UI 설정에는 실제 지원되는 메뉴만 표시하기로 합의했다.

**다음 단계에서 결정해야 할 질문(아직 미확정)**:

1. 계정 없이 사용(게스트 모드)을 허용할지, 첫 실행부터 회원가입을 강제할지; 기존 사용자 데이터는 반드시 잃지 않도록.
2. 로그인 방법: 이메일/비밀번호, 이메일 매직 링크, 플랫폼 제공 OAuth 등 중 MVP 범위. 방식별 계정 복구 정책.
3. 로그인 유지와 로그아웃: 운동 중 연결/인증 만료를 어떻게 처리하고 진행 중 운동을 보호할지.
4. 기존 로컬 기록 → 신규 계정으로 **명시적 승인 후 이전**. 동일 기록 ID 중복, 서버 기록과 로컬 기록 충돌, 부분 완료/활성 세션, 재시도/중단/복구, 실패 시 원본 유지. 여러 기기/여러 계정 사용 시 동작.
5. 계정 전환/로그아웃 시 같은 브라우저의 이전 사용자 로컬 기록이 다른 사용자에게 노출되지 않게 하는 정책. 로그아웃만으로 근거 없이 데이터를 영구 삭제하면 안 됨.
6. 회원 탈퇴/데이터 내보내기와 복구, 개인정보 최소 수집 정책 및 사용자 안내.
7. 인증/서버 API 단계에서 HTTPS, 안전한 세션/쿠키, CSRF, 계정별 서버 소유권 검증, 중복 전송 방지와 idempotency 보장 등의 기술적 설계.

**Task 005.5 산출물 추천**: (a) 화면/동선 지도, (b) 로그인/회원가입/복구/로그아웃 상태표, (c) 로컬 데이터 이전·충돌 수용 시나리오, (d) Task 006용 인증/데이터 경계 요구사항. **코드 구현이나 DB 설계를 미리 시작하지 않는 것이 원칙.**

## 10. 협업 및 문서 관리 규칙

- ChatGPT에서 방향·수용 기준을 명확히 결정한 후 Codex에게 **독립적으로 실행 가능한 Task 프롬프트** 제공.
- Codex는 `AGENTS.md`와 저장소의 `docs/product/`를 기준으로 계획→구현→테스트→자체 검토→보고. 새 Git Commit/Push/배포는 별도 지시 전 금지.
- 프론트·백엔드 Git 저장소를 혼동하지 않음. 사용자가 의도한 LAN host 설정, Health 코드 및 기존 운동 데이터 보존.
- `docs/product/` = 최신 제품 명세, `docs/tasks/` = 프롬프트·보고서·증거, `docs/handoff/` = 단계별 인수인계. 보고서의 이전 구현 설명이 최신 제품 합의와 다른 경우 `docs/product/`와 현재 코드가 우선.
- Task 005는 사용자가 Git **커밋했다**고 알려줌. Push까지 했는지, 새 커밋 해시/청결 상태는 필요할 때 실제 저장소에서 재확인.
