# Task 004 — 진행 중량 변경 이력 및 빠른 중량 입력 결과

- 작업: 2026-10-26~27 (Asia/Seoul)
- 요청 문서: `overload-task-004-progression-history-followup.md`
- 범위: `overload-pwa`의 기존 Task 004 미커밋 변경 위에 후속 구현
- 상태: 구현·자동 검사·데스크톱 브라우저 검증 완료. 실제 iPhone 검증은 남음.

## Summary

운동 당시 판정, 현재 승인 중량의 검토 상태, 실제 승인한 중량 변경 사건을 분리했다. 기록 상세의 당시 판정은 완료 세션의 스냅샷을 사용하고, 기록 탭과 홈의 현재 검토는 현재 루틴·배치·중량에 맞는 근거만 사용한다. 루틴 편집과 운동 화면에서 성공적으로 승인한 변경은 별도의 이력으로 남는다.

중량 입력은 신규 루틴 최초 중량, 기존 루틴 진행 중량 초안, 운동 중 중량 모달에 공통 컨트롤을 적용했다. 중앙 직접 입력과 좌우 ±2.5kg 버튼을 제공하며, 버튼은 초안만 바꾼다. 실제 승인은 기존 `루틴 저장` 또는 운동 모달의 명시적 확인에서 이루어진다.

## Changes

### 과거 판정과 현재 검토

- 세션 상세 하단에 `이 운동의 중량 검토 결과`를 추가했다. 당시 승인 중량, 실제 반복 횟수, 목표 범위와 함께 `당시 증량 가능`, `당시 감량 검토`, `당시 유지`를 표시한다.
- 전체 계획 미완료 또는 계획 수 미확인, 본세트 구성 변경, 일시·혼합 중량 기록에는 판정 불가 이유를 표시한다. 부분 기록을 전역 감량 검토로 사용하지 않는다.
- 기존 완료 세션의 승인 중량·세트·목표 범위를 읽으며 현재 승인 중량으로 과거를 다시 계산하지 않는다. 이후 중량 승인으로 과거 세트와 benchmark를 수정하지 않는다.
- 기록 탭에는 적용 가능한 항목이 있을 때만 `현재 중량 조정 검토`와 `진행 중량 변경 내역`을 표시한다. 홈은 같은 파생 함수를 현재 선택 루틴에 한정하여 재사용한다.
- 현재 검토는 `routineId + placementId + exerciseId + setCount + minReps + maxReps + approvedWeight` 조건으로 비교한다. 기존 `increaseBenchmark`와 `recommendation`을 재사용하고 세트별 최고 횟수를 합성하지 않는다.
- 강한 기준 기록과 약한 최근 비교 가능 기록이 함께 있으면 두 근거를 각각 보여 준다. 검토 표시만으로 중량을 자동 변경하지 않는다.

### 승인 변경 이벤트와 v1 호환성

`WorkoutState.progressChanges`는 선택 필드다. 각 사건은 다음 값을 보존한다.

| 필드 | 의미 |
| --- | --- |
| `id`, `occurredAt` | 사건 식별자와 승인 시각(epoch milliseconds) |
| `routineId`, `placementId` | 변경 대상 루틴과 종목 배치 |
| `routineName`, `exerciseName` | 승인 당시 이름 스냅샷 |
| `previousApprovedWeight`, `nextApprovedWeight` | 변경 전후 승인 중량 |
| `source` | `routine_editor` 또는 `workout` |
| `relatedSessionId?` | 운동 화면에서 명확히 얻을 수 있는 활성 세션 ID만 기록 |

- 이름 변경·루틴 삭제 후에도 저장된 이름과 변경 사건은 유지한다. 같은 종목을 쓰는 다른 루틴의 배치는 분리한다.
- 루틴 편집은 한 저장에서 실제로 바뀐 배치마다 사건 한 건을 추가한다. 운동 화면도 실제 승인 중량이 달라질 때만 한 건을 추가한다.
- 최초 중량 설정, 오늘만 변경, 미저장 초안, 취소, 동일 값 저장, 검증 오류에는 사건을 추가하지 않는다.
- 기존 `overload.core.v1` 키와 버전을 유지한다. 필드가 없는 데이터는 빈 이력으로 읽고, 로드만으로 다시 저장하거나 과거 사건을 추측하여 생성하지 않는다.
- 신규 필드가 있으면 식별자·중복 ID·이름·유한한 0 이상 중량·변경 전후 차이·시각·출처·세션 연결을 검증한다. 손상된 원본은 기존 저장 차단 정책으로 보호한다.

### 실패·재시도·충돌 방어

- 승인 중량과 사건 배열은 기존 단일 localStorage 값에 함께 저장한다. 승인 사건을 추가하는 쓰기가 실패하면 이전 상태 전체를 유지한다. 승인 중량만 바뀌거나 저장되지 않은 사건이 완료 이력으로 보이지 않는다.
- 루틴 편집 입력과 운동 모달 초안은 보존한다. 운동 모달은 승인 실패 시 닫히지 않고 오류를 보여 준다.
- 실패 후 `저장소 재확인`은 이전 상태의 저장 가능 여부만 확인한다. 취소되거나 오래된 승인 후보를 자동 재실행하지 않는다. 사용자가 다시 명시적으로 저장·승인했을 때 한 건을 기록한다.
- 일반 운동 입력의 저장 실패는 기존처럼 화면 입력을 유지한다. 승인 실패의 전체 되돌림과 구분한다.
- 다른 탭의 저장 이벤트가 발생하면 기존 편집 차단을 유지한다. 이 구현은 브라우저의 단일 키 저장 및 기존 탭 충돌 방어 범위이며 서버 트랜잭션이나 분산 환경의 exactly-once 보장은 아니다.

### 중앙 중량 입력

- 재사용 `WeightInput`: `[ −2.5 ] [ 직접 편집 가능한 숫자 · kg ] [ +2.5 ]`.
- 중앙 입력은 `inputMode="decimal"`, 명시적인 접근성 이름과 `중량 직접 입력` 설명을 제공한다. 좌우 버튼은 `중량 2.5kg 감소/증가` 레이블을 갖는다.
- 버튼 터치 영역은 52×52 CSS px다. 버튼은 input에 강제 포커스를 주거나 저장·완료·모달 닫기를 수행하지 않는다.
- 0 또는 1kg에서 감소를 비활성화한다. 빈 값, 소수점만 입력한 상태, 유효하지 않은 문자열에서는 양쪽 조절을 비활성화하며 임의의 기본값을 넣지 않는다.
- 61.3kg 같은 직접 입력에 ±2.5를 그대로 적용한다. BigInt 기반 십진 연산으로 조절값과 변화량 표시에 부동소수 오차가 노출되지 않도록 했다. Number 범위를 벗어나거나 값이 달라지지 않는 조절도 비활성화한다.
- 2.5kg은 입력 편의 단위이며 새로운 증량 정책이나 자동 승인 규칙이 아니다.

## Notes 및 남은 검증

추가 승인 요청은 불필요했고 보류한 구현은 없다. 실제 iPhone Safari/Home Screen PWA 환경은 사용하지 않았으므로 숫자 키패드 종류, 키보드가 열린 상태의 고정 CTA·모달 가림, Safe Area, 실제 터치 동작을 검증 완료로 주장하지 않는다. 실제 기기에서는 세 입력 경로의 중앙값 탭→소수 입력, ±2.5, 취소·승인, 키보드 열림/닫힘과 하단 조작을 확인해야 한다.

현재 본세트 정책은 완료 세션의 불변 필드로 당시 판정을 재현할 수 있어 별도의 영구 판정 스냅샷은 추가하지 않았다. Task 005에서 판정 정책이 달라지거나 드랍세트 등이 도입되기 전에 정책 버전과 판정·근거 스냅샷 저장을 설계해야 한다. 기존 세션에는 확인 가능한 사실만 사용한다.

Task 005 PostgreSQL 설계에서는 `progressChanges`를 독립 이벤트 테이블로 옮기고 사용자 소유권, 루틴/배치 식별자, 이름 스냅샷, 발생 시각, 전후 중량, 출처, 선택 세션 연결을 유지한다. 승인 상태 갱신과 사건 삽입의 DB 트랜잭션, 재전송 idempotency key/unique 제약 및 동시 수정 처리를 함께 설계해야 한다. 관련 세션 ID는 조작이 일어난 세션을 뜻하며 운동 결과가 변경을 유발했다는 인과관계로 사용하지 않는다.
