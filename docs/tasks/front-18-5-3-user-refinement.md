## 홈 루틴 선택·시작 오류

4173의 검수 브라우저에서 Spring 조회를 사용하며 브라우저 응답만 격리한 시나리오로 재현했다. 휴식일을 표시하도록 일정 응답을 조정하고, 루틴 상세와 디로딩 상태의 503을 각각 재현했다. 어느 경우에도 서버 일정·루틴을 쓰지 않았다.

| 재현 조건 | 5-3 수정 전 | 5-3B 변경 |
| --- | --- | --- |
| 휴식일, 모든 루틴 상세 조회가 503 | 목록 13개가 비활성화되고 상세 조회 오류 안내 없이 휴식일로 표시 | 목록에서 확인할 수 없는 루틴을 잠그고 시작 버튼을 비활성화한다. 상단에 `루틴 구성을 불러오지 못했어요.`와 기존 새로고침 조작을 표시한다. |
| 디로딩 기간 상태 조회가 503 | 조회 실패의 `undefined`를 `protection !== null`로 검사하므로 실제 디로딩 보호처럼 목록 전체가 잠김 | 확인한 `ACTIVE`·`COMPLETED`에만 디로딩 선택 잠금을 적용한다. 상태를 확인하기 전 START는 계속 차단하고 기존 조회 실패 Toast를 쓴다. |
| 정상 휴식일 | 유효한 대체 루틴은 선택할 수 있고 시작 버튼은 선택 후 노출 | 선택 전에는 시작 버튼을 비활성화하고 휴식 안내를 표시한다. 선택에 성공하면 해당 루틴을 표시하고 시작을 활성화한다. |
| 최신 홈 계획 조회 전·후 | 캐시와 계획 표시, 버튼과 실제 요청 검사 기준이 서로 달라질 수 있음 | 검증된 루틴 버전과 `training.canWrite`를 홈의 새 START에 사용한다. 재조회 중 기존 계획을 표시하되 최신 확인을 기다린다. |

루틴 상세는 개별 루틴의 최신 버전을 다시 확인한 뒤 기존 START 경로를 탄다. 홈은 여기에 오늘 일정과 계정의 쓰기 가능 상태를 확인한다. 진행 운동 이어가기, 중복 방지, 응답 미확인 재확인은 기존 경로를 유지했다. 사용자가 본 `휴식일 + 목록 전체 잠김 + 시작 활성`의 정확한 조합과 이전 간헐 오류의 직접 원인은 미확정이다. [수정 전 Spring·브라우저 재현](evidence/front-18-5-3-refinement/spring-before.json)
